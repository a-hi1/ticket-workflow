# 客服工单工作流 · 7 节点编排

一个可以跑的工单分流工作流：**意图分类 → 条件分流 → 知识库检索 → 兜底判定 → 草稿生成**。

单文件 · 零依赖 · 无后端 · 不调用任何模型

---

## 在线体验

> https://a-hi1.github.io/ticket-workflow/

---

## 节点

| # | 节点 | 作用 |
|---|---|---|
| 01 | 开始 | 接收工单文本 |
| 02 | 意图分类 | 5 类加权关键词：退款退货 / 物流查询 / 商品咨询 / 投诉建议 / 其他 |
| 03 | 条件分支 | `class == 商品咨询` 走向检索，其余直接生成 |
| 04 | 知识库检索 | 10 条商品 FAQ，字符二元组覆盖率打分 |
| 05 | 兜底判定 | 覆盖率 < 0.30 → **转人工** |
| 06 | 草稿生成 | ≤120 字、仅引用检索原文、不承诺赔付 |
| 07 | 输出 | `{class, draft, need_human}` |

---

## 为什么这么设计

### 1. 用条件分支，不让模型判断走向

模型判断不可控也不可解释。分支是确定性的：**分类错了能定位到具体节点**，而不是整条链路都说不清。

### 2. 宁可转人工，不让模型编

检索覆盖率低于 0.30 时直接置 `need_human`，不进入生成节点。
客服场景里，**编错一句话就是赔付问题**。

### 3. 批量跑，单条失败不影响整体

20 条样本一次跑完，逐条给结果，不是整批中断。

---

## 实测结果

20 条样本：**成功 18 条，转人工 2 条（成功率 90%）**

转人工的两条：

| 工单 | 覆盖率 | 为什么 |
|---|---|---|
| 你们的耳机和别家比怎么样，值得买吗 | 0.13 | 需要横向对比，知识库只有单品参数 |
| 这副耳机适不适合给老人用 | 0.09 | 需要人群适配判断，知识库无此维度 |

这两条**看起来都是商品咨询，但知识库答不了** —— 这正是加兜底分支的原因。

---

## 已知不足

- 分类是**加权关键词**，不是语义理解：说「下载账单」识别不出是导出
- 检索是**字符二元组覆盖率**，同义词换一种说法可能匹配不上
- 没有真实工单数据，20 条样本是构造的

> 这些不足是刻意的：演示要在任何环境下都能跑，所以不接模型。
> 真实项目里这两处都会换成模型 + 向量检索。
